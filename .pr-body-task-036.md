## Summary

One-time bulk import of 173 public-domain English Hymnal hymns into the `songs` table, plus the supporting infrastructure to run it idempotently.

- **Pure parser** (`scripts/parsers/hymnsMarkdownParser.ts`) — splits the source markdown into 173 hymn records, resolves all escape sequences, and normalizes section headers to the Saliw chord-sheet format (`[VERSE N]`, `[CHORUS]`, `[REFRAIN]`).
- **CLI seeder** (`scripts/import-hymns.ts`) — service-role Supabase client, batched UPSERT (50/batch) on `(title, artist)`, `--dry-run` flag, env vars loaded via `tsx --env-file=...local`.
- **Migration** (`20260503000001_songs_title_artist_unique_index.sql`) — UNIQUE INDEX on `songs(title, artist)` to enable conflict resolution. **No RLS policy changes.**
- **Tooling** — adds `tsx`, `dotenv`, `vitest` as devDeps; new scripts `import:hymns`, `test:unit`, `format:scripts`.

## Why

User had 173 traditional hymns in markdown form and wanted them in the Saliw song library. Direct SQL import was rejected because `original_key` and `artist` are NOT NULL in the schema, and 170 of the 173 hymns are lyrics-only (would fail `hasValidChordContent()` in `createSong`). A seed script bypasses validation via service-role insert and handles escaping safely.

## New prevention pattern (BUG-016)

The validator-agent surfaced a class of issue worth recording: when a UNIQUE INDEX is added to a table mutated by Server Actions, the corresponding actions need explicit handling for PostgreSQL error code `23505` before the generic catch-all. `createSong` in `src/app/actions/songActions.ts:74–83` currently maps duplicates to the generic "Unable to create song. Please try again." Reference good pattern: `setlistActions.ts:803`. Tracking as a separate follow-up — not in scope for this PR.
